# Staging server

How to set up the ReelGuo staging site on a Windows cloud server with Docker, behind Cloudflare, and how to keep it
updated. Everything runs from scripts in `scripts\staging\`; this guide explains each step and what to do when
something goes wrong.

Staging is a copy of production for testing and review:

- It runs the same containers as production (`infra/docker-compose.yml`, profile `app`) with a staging overlay
  (`infra/docker-compose.staging.yml`).
- It holds **demo content**: labelled sample series generated by ffmpeg, with no real people. The real catalogue is
  still under review.
- It stays **out of search engines**: robots.txt disallows everything and every page says noindex.
- Media is stored on the server's disk (a Docker volume), not in S3.

```
 Visitors ──https──▶ Cloudflare ──(Cloudflare Tunnel, outbound from the server)──▶ cloudflared container
                                                                                        │
                       ┌────────────────────────── Docker on the Windows server ────────▼────────────┐
                       │  web (Caddy): app :8080, admin :8081 ──▶ api (ASP.NET) ──▶ postgres          │
                       │                                          worker (ffmpeg)    volumes: media,  │
                       │  backup (nightly pg_dump)                                   pgdata, backups  │
                       └──────────────────────────────────────────────────────────────────────────────┘
```

| Script | When |
|---|---|
| `setup.ps1` | Once, to set the server up (safe to run again) |
| `update.ps1` | For every new version |
| `rollback.ps1` | When an update went wrong |
| `ops.ps1` | Day to day: status, logs, restart, backups |
| `seed-demo.ps1` | (Re)load the demo content |

Run them from the repository folder in PowerShell. If Windows blocks scripts, start them as
`powershell -ExecutionPolicy Bypass -File .\scripts\staging\<script>.ps1 ...`.

---

## 1. What you need

**The server**

- A Windows cloud VM (Windows Server 2022/2025 or Windows 11). At least 4 vCPU, 8 GB RAM and 60 GB of free disk:
  the images take about 6 GB, and the media and backup volumes grow with content.
- **Docker running Linux containers**: the same setup used now. That is Docker Desktop with the WSL 2 backend, or
  Docker Engine inside WSL 2. Docker Compose must be **2.24.4 or newer** (`docker compose version`).
- Docker must start by itself after a reboot (Windows updates restart the server). With Docker Desktop, turn on
  *Settings → General → Start Docker Desktop when you sign in*, and set up automatic sign-in for the account that
  runs it, or run Docker Engine as a service. The containers restart on their own once Docker is up.
- **Git for Windows**, to fetch new versions. Not needed if you copy the code over by hand (see §3).
- PowerShell 5.1 or newer (built into Windows).

**Cloudflare**

- The domain is on Cloudflare.
- Cloudflare Zero Trust is set up; the free plan is enough. Visitors reach the server through a Cloudflare Tunnel, so
  no port has to be opened on the server or in the cloud firewall.

**The code**

- Read access to the ReelGuo repository from the server, for example a read-only deploy key or access token.
- The version to deploy pushed to a branch (for example `main`, or a `staging` branch).

## 2. First-time setup (about 30–45 minutes)

### Step 1. Create the Cloudflare Tunnel

1. In the Cloudflare dashboard, go to **Zero Trust → Networks → Tunnels → Create a tunnel**, choose **Cloudflared**,
   and name it `reelguo-staging`.
2. On the "install connector" page, copy the **token**: the long string after `--token` in any of the install
   commands. **Do not run Cloudflare's installer.** The setup script runs the connector in Docker.
3. Leave the page at "Public hostnames" for now; you come back to it in step 4.

### Step 2. Get the code onto the server

Open PowerShell on the server, then:

```powershell
git clone <repository URL> C:\reelguo
cd C:\reelguo
git checkout main          # or the branch staging should follow
```

A path without spaces, such as `C:\reelguo`, avoids quoting problems later.

### Step 3. Run the setup

```powershell
.\scripts\staging\setup.ps1 -AppUrl https://staging.yourdomain.com -TunnelToken <token from step 1>
```

The script:

1. **Checks the server.** Docker must be running Linux containers, Compose must be new enough, and it looks at free
   disk space.
2. **Writes `infra\staging.env`.** It starts from `infra\staging.env.example`, fills in the address and tunnel
   token, and generates new secrets: the media signing key, the sign-in key and the admin password. Access to the
   file is limited to you and Administrators. If the file already exists, its values and secrets are kept.
3. **Builds the images.** This takes 5–15 minutes the first time.
4. **Starts everything:** database, API, worker, web, nightly backups and the tunnel connector.
5. **Waits until the site is ready.** The database is created on the first start.
6. **Checks the site:** the pages, that robots.txt keeps search engines out, the API, the admin console and the
   tunnel connector.
7. **Loads the demo content:** 4 series × 5 episodes, encoded by the worker, then published, plus sample posts. Use
   `-SkipDemo` to leave it out.

At the end it prints the **admin password** once. Save it in your password manager; it is also in
`infra\staging.env` as `REELGUO_ADMIN_PASSWORD`.

The script is safe to run again, for example after fixing a problem: it keeps the settings and data.

### Step 4. Point the staging address at the tunnel

Back in **Zero Trust → Networks → Tunnels → reelguo-staging → Public hostname → Add a public hostname**:

| Field | Value |
|---|---|
| Subdomain / Domain | `staging` / `yourdomain.com` (must match `-AppUrl`) |
| Service type | `HTTP` |
| URL | `web:8080` |

Cloudflare creates the DNS record itself.

The admin console isn't public. On the server, open **http://localhost:8081**; use `localhost`, not `127.0.0.1`,
because the sign-in cookie needs it. To reach it from elsewhere, add a second public hostname, for example
`staging-admin` → `HTTP` `web:8081`. **Protect it before using it:** **Zero Trust → Access → Applications → Add an
application → Self-hosted**, for that hostname, with a policy that allows only your team's email addresses.

### Step 5. Cloudflare settings for the domain

- **SSL/TLS → Edge Certificates → Always Use HTTPS**: on.
- **Network → IP Geolocation**: on (the default). The site reads the visitor's country from it, for the country block
  list and the age rules.
- **Caching:** don't add "Cache Everything" rules for the staging host. Pages differ per country and per visitor;
  static files are cached correctly by default.

### Step 6. Check the site

- Open `https://staging.yourdomain.com`. The 18+ page appears; after confirming, the demo series are on the home
  page and play.
- `https://staging.yourdomain.com/robots.txt` must show `Disallow: /`.
- Sign in to the admin console with user `admin` and the password from step 3.
- Run `.\scripts\staging\ops.ps1 status`. Every line should say `ok`.

### Step 7. After the first sign-in

- Create named admin accounts for the team (**管理员**), then change the `admin` password there.
- If you change it, `seed-demo.ps1` needs the new one: `seed-demo.ps1 -AdminPassword <new password>`.
- Keep a copy of `infra\staging.env` in your password manager. Without `REELGUO_MEDIA_KEY` and `REELGUO_JWT_KEY` a
  rebuilt server can't continue where this one left off.

### Without a tunnel (public port)

If the tunnel can't be used, Cloudflare can reach the server directly on port 80:

1. Run `setup.ps1 -Mode public-port -AppUrl https://staging.yourdomain.com`. The site then listens on port 80 of
   every network interface.
2. In Cloudflare **DNS**, add an `A` record `staging` → the server's public IP, **Proxied** (orange cloud). Under
   **SSL/TLS**, choose **Flexible**: the server itself speaks plain HTTP.
3. **Allow port 80 only from Cloudflare.** Otherwise anyone can reach the server directly, bypass Cloudflare, and fake
   the country and IP headers. Set this both in the cloud provider's firewall (security group) and in Windows:

   ```powershell
   $ranges = @((Invoke-RestMethod https://www.cloudflare.com/ips-v4) -split "`n") + @((Invoke-RestMethod https://www.cloudflare.com/ips-v6) -split "`n") | Where-Object { $_ }
   New-NetFirewallRule -DisplayName 'ReelGuo staging (Cloudflare only)' -Direction Inbound -Protocol TCP -LocalPort 80 -RemoteAddress $ranges -Action Allow
   ```

   Then confirm from another machine that `http://<server IP>/` does **not** answer. Docker Desktop can add its own
   firewall rules, so the cloud firewall is the one to rely on.

The tunnel is simpler and safer; use this only when it isn't possible.

## 3. Updating staging (every new version)

1. Push the new version to the branch staging follows.
2. On the server, in the repository folder:

   ```powershell
   .\scripts\staging\update.ps1
   ```

The script:

1. **Checks** Docker and the settings.
2. **Fetches the code** with `git pull --ff-only`. It stops if someone has edited files on the server; see §7.
3. **Keeps the running images** as `:rollback`, for `rollback.ps1`.
4. **Backs up the database.** The backup goes in the same place, and has the same format, as the nightly ones. If the
   backup fails, it stops before changing anything.
5. **Builds the new images and restarts what changed.** Database migrations run when the API starts.
6. **Waits until the site is ready** and runs the same checks as the setup.
7. **Removes unused image layers.**
8. **Records the deploy** in `infra\staging.deploy.log`: time, action, commit and result.

An update usually takes 3–10 minutes, and the site is unavailable for about a minute while the containers restart.

| Option | Use |
|---|---|
| `-Ref <branch>` | Switch to another branch and follow it, for example `-Ref release/1.2`. |
| `-Ref <tag or commit>` | Deploy one fixed version, for example `-Ref v1.2.0`. Plain updates then stop until you choose a branch again with `-Ref main`. |
| `-SkipPull` | Deploy the code already in the folder, for example copied over by hand without git. |
| `-SkipBackup` | Skip the database backup (not advised). |
| `-AllowDirty` | Continue although files were changed on the server. |

Changed only `infra\staging.env`? You don't need an update: run `.\scripts\staging\ops.ps1 start`, which restarts the
containers whose settings changed.

### If an update fails

When the new version doesn't become ready, the script prints the recent logs and the two ways back. It doesn't roll
back by itself, because the database may already have been migrated:

```powershell
.\scripts\staging\rollback.ps1                                   # the previous images, database as it is
.\scripts\staging\rollback.ps1 -RestoreBackup <backup file>      # the previous images and the database from before the update
```

The backup file name is printed by `update.ps1`, in step 4 and again in the failure message.

## 4. Rolling back

| Command | What it does |
|---|---|
| `rollback.ps1` | Starts the images that ran before the last update. The database isn't touched. Use it when the update failed before changing the database, or when the change is compatible. |
| `rollback.ps1 -ListBackups` | Lists the backups on the server, newest first. |
| `rollback.ps1 -RestoreBackup <file>` | Previous images, **and** the database replaced by that backup in one all-or-nothing step. Everything saved after the backup is lost (new accounts, comments, admin edits); media files are kept. It asks you to type the file name to confirm (`-Yes` skips that). |

Rolling back doesn't change the code folder. Before the next update, check out the version you want; the commits
are listed in `infra\staging.deploy.log`.

## 5. Day to day

| Command | What it does |
|---|---|
| `ops.ps1 status` | Containers, readiness, the site checks, and the last deploys. |
| `ops.ps1 logs [service]` | Follows the logs; Ctrl+C to stop. Services: `api`, `worker`, `web`, `postgres`, `backup`, `cloudflared`. |
| `ops.ps1 restart [service]` | Restarts one service, or everything. |
| `ops.ps1 stop` / `ops.ps1 start` | Stops everything with the data kept, or starts again. `start` also applies changed settings. |
| `ops.ps1 backup` | Backs up the database now. |
| `ops.ps1 backups` | Lists the backups. |
| `ops.ps1 disk` | Disk used by images, containers and volumes. |

**Backups.**
- **Schedule:** the `backup` container dumps the database once a day and keeps 14 days, in the `reelguo-staging_backups` volume.
- **Off-site copy:** set `REELGUO_BACKUP_REMOTE` and its rclone settings (see `infra/backup/backup.sh`). Add `REELGUO_BACKUP_PING_URL` to get an alert when backups stop.
- **Testing a backup:** `docker compose -p reelguo-staging --env-file infra\staging.env -f infra\docker-compose.yml -f infra\docker-compose.staging.yml --profile app run --rm backup "sh /scripts/restore-test.sh"`.

**Demo content.**
- `seed-demo.ps1` skips when published series exist; `-Force` adds another set.
- When the reviewed catalogue arrives, take the demo series and posts down in the admin console (**内容管理**, **吃瓜文章**). They are titled "（示例）".

**Disk space.** Watch the free space on the Docker disk. `update.ps1` removes unused image layers. The media volume
(`reelguo-staging_media`) grows with every upload, and the backups take about 14 × the database size.

**After a server restart.** Once Docker is running, the containers start on their own. Check with `ops.ps1 status`.

## 6. Settings reference (`infra\staging.env`)

| Setting | Meaning |
|---|---|
| `REELGUO_APP_URL` | The staging address (`https://…`, no trailing slash). Used for canonical links, payment returns and the apps' address list. |
| `REELGUO_STAGING_MODE` | `tunnel` (default) or `public-port`. |
| `CLOUDFLARE_TUNNEL_TOKEN` | The tunnel connector's token (tunnel mode). |
| `REELGUO_WEB_BIND`, `REELGUO_ADMIN_BIND` | Where the app and the admin console listen on the server. Tunnel: `127.0.0.1:8080` / `127.0.0.1:8081`. Public port: `0.0.0.0:80`. |
| `REELGUO_MEDIA_KEY`, `REELGUO_JWT_KEY` | Signing keys, generated once. Changing them signs everyone out and breaks issued media links. |
| `REELGUO_ADMIN_PASSWORD` | Password of the first admin account `admin`. It is only used to create that account, on the first start. |
| `REELGUO_ALLOW_INDEXING` | Keep `false` on staging. |
| `REELGUO_PERMANENT_DOMAIN`, `REELGUO_TELEGRAM`, `REELGUO_CONTACT_EMAIL` | Official addresses shown on the site (footer, 回家的路). Optional. |
| `REELGUO_BILLING_ENABLED`, `REELGUO_PAYMENT_PROVIDER`, `REELGUO_ALLOW_SANDBOX_PAYMENTS`, `REELGUO_SANDBOX_SECRET` | Off by default. To try paid episodes and the store with the sandbox provider, set them to `true`, `sandbox`, `true` and a long random string. Anyone can then "pay" for free, so use this on staging only. |
| `REELGUO_BACKUP_REMOTE`, `REELGUO_BACKUP_PING_URL` | Optional off-site backup copy, and an alert when backups stop. |
| `CLOUDFLARED_IMAGE` | (Optional) Pin the connector to a version tag listed on Docker Hub (`cloudflare/cloudflared:<version>`); the default is `latest`. |

After editing the file, run `ops.ps1 start`.

## 7. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| "Docker runs windows containers" | Docker Desktop is in Windows-container mode. Right-click its tray icon → **Switch to Linux containers**. |
| "docker compose … is too old" | Update Docker Desktop; Compose 2.24.4 or newer is needed. |
| The build fails while downloading | Network or DNS on the server; run the same script again. Docker Hub rate limits: sign in with `docker login`. |
| "The site did not become ready" | Read the printed logs, or `ops.ps1 logs api`. Usual causes: the database didn't start (disk full), or a value is missing in `infra\staging.env`. |
| Cloudflare error **1033** | The tunnel isn't connected. Check `ops.ps1 logs cloudflared`; usually a wrong or old token. Copy it again from the tunnel's page, put it in `CLOUDFLARE_TUNNEL_TOKEN`, then run `ops.ps1 start`. |
| Cloudflare **502 Bad Gateway** | The public hostname's service is wrong. It must be `HTTP` and `web:8080` (admin: `web:8081`), not `localhost`. |
| Cloudflare **521** (public-port mode) | The server isn't reachable on port 80. Check the firewall rule includes Cloudflare's ranges, and that `REELGUO_WEB_BIND` is `0.0.0.0:80`. |
| Every visitor's country is "XX", or country rules don't apply | IP Geolocation is off in Cloudflare (Network settings). |
| Can't stay signed in to the admin console on the server | Open `http://localhost:8081`, not `127.0.0.1`. The sign-in cookie needs a secure address, and browsers count `localhost` as one. |
| `seed-demo.ps1` fails | Check `ops.ps1 logs worker` (it encodes the clips). If the admin password was changed, pass it with `-AdminPassword`. |
| update: "There are uncommitted changes" | Files were edited on the server. Look with `git status`. Discard with `git checkout -- .`, or commit them to the repository instead. |
| update: "This folder is on a fixed version" | It was last deployed with `-Ref <tag>`. Run `update.ps1 -Ref main` to follow a branch again. |
| The disk is full | `ops.ps1 disk`. Remove old images with `docker image prune -a` (keeps the ones in use). Check the media and backups volumes. |

## 8. Security notes

- **`infra\staging.env` holds the secrets.** It is git-ignored and limited to your account and Administrators. Keep a
  copy in a password manager, and never paste it into tickets or chats.
- **The admin console is local-only:** `127.0.0.1:8081` on the server. Publish it only through the tunnel, behind a
  Cloudflare Access policy.
- **The database and Redis have no published ports.** They are reachable only inside Docker.
- **Staging stays out of search engines.** Check after changes that `/robots.txt` says `Disallow: /`.
- **Sandbox payments are off.** If you turn them on for testing, anyone can top up for free, so never on production.
- **Production differs from staging.** Production follows `docs/RUNBOOK.md` §10 (Before launch): a CDN for media, S3
  storage, real payments, `REELGUO_ALLOW_INDEXING=true`, monitoring.
