# Staging server

How to set up the ReelGuo staging site on a Windows server, behind Cloudflare, and how to keep it updated.
Everything is installed natively on Windows as Windows services, without Docker. The cloud server can't run
containers: it has no nested virtualization, so WSL 2 and Docker Desktop don't work there. Everything is done by the
scripts in `scripts\staging\`; this guide explains the steps and what to do when something goes wrong.

Staging is a copy of production for testing and review:

- **Demo content.** Labelled sample series, generated by ffmpeg, with no real people. The real catalogue is still
  under review.
- **Out of search engines.** robots.txt disallows everything and every page says noindex.
- **Storage.** Images and the demo videos are kept on the server's disk. The real videos go to **Tencent COS**
  (§6): the admin's browser uploads them straight to the bucket, and viewers play them from there.

```
 Visitors ──https──▶ Cloudflare ──(Cloudflare Tunnel: outbound from the server)──▶ cloudflared service
                                                                                         │
       ┌──────────────────────────── Windows services on the server ──────────────────────▼──────────────┐
       │  ReelGuoWeb (Caddy): app 127.0.0.1:8080, admin 127.0.0.1:8081 ──▶ ReelGuoApi (127.0.0.1:5080)     │
       │  ReelGuoWorker (ffmpeg encoding)            postgresql-x64-17 (127.0.0.1:5432)                     │
       │  Scheduled task "ReelGuo staging backup" (nightly pg_dump)                                          │
       └────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

**Where things are**

| Path | Contents |
|---|---|
| `C:\reelguo` | The code (a git clone). Releases are built from it. |
| `C:\reelguo-staging\staging.env` | Settings and secrets. The folder is readable only by SYSTEM and Administrators. |
| `C:\reelguo-staging\releases\<time>-<commit>\` | One folder per built version: `api`, `worker`, `web\client`, `web\admin`, `Caddyfile`. The last 5 are kept. |
| `C:\reelguo-staging\current` | A link to the running release. A rollback points it back. |
| `C:\reelguo-staging\data\storage` | Videos and images. |
| `C:\reelguo-staging\backups` | Database backups (nightly, kept 14 days). |
| `C:\reelguo-staging\tools` | Caddy (web server) and ffmpeg. |
| `C:\reelguo-staging\logs\caddy.log` | Web server log. The API and worker log to the Windows Event Log (Application). |
| `C:\Program Files\PostgreSQL\17` | PostgreSQL and its data. |

**Scripts.** Run them in **PowerShell as Administrator** from `C:\reelguo`. If Windows blocks scripts, run
`Set-ExecutionPolicy -Scope Process Bypass` first.

| Script | When |
|---|---|
| `setup.ps1` | Once, to set the server up (safe to run again) |
| `update.ps1` | For every new version |
| `rollback.ps1` | When an update went wrong |
| `ops.ps1` | Day to day: status, logs, restart, settings, backups |
| `seed-demo.ps1` | (Re)load the demo content |
| `backup.ps1` | One database backup (run nightly by the scheduled task) |

## 1. What you need

- **The server.** Windows Server 2022 or 2025 (or Windows 10/11), with an Administrator account.
  - 2+ vCPU, 4 GB RAM (8 GB builds faster), and at least 60 GB free on C:.
  - **winget** (App Installer). It is built into Windows Server 2025 and Windows 11.
  - Internet access to GitHub, nuget.org, the npm registry, caddyserver.com, gyan.dev (ffmpeg),
    enterprisedb.com (PostgreSQL) and Cloudflare.
- **Cloudflare.** The domain is on Cloudflare, and Cloudflare Zero Trust is set up (the free plan is enough). With a
  tunnel, no inbound port has to be opened. Without one, proxied DNS records point at the server and port 80 is open
  to Cloudflare only (see "Without a tunnel" in §2).
- **The code.** Read access to the ReelGuo repository from the server (a read-only deploy key or access token), and
  the version to deploy pushed to a branch, for example `main`.

`setup.ps1` installs everything else: Node.js (with pnpm), the .NET 10 SDK, cloudflared, PostgreSQL 17, Caddy and
ffmpeg. The scripts run in the Windows PowerShell 5.1 that comes with Windows; PowerShell 7 works too.

## 2. First-time setup (about 30–60 minutes)

### Step 1. Create the Cloudflare Tunnel

1. In the Cloudflare dashboard, go to **Zero Trust → Networks → Tunnels → Create a tunnel**, choose **Cloudflared**,
   and name it `reelguo-staging`.
2. On the "install connector" page, copy the **token**: the long string after `--token` in the install command.
   **Don't run Cloudflare's installer.** The setup script installs the connector itself.

### Step 2. Install Git and get the code

In PowerShell as Administrator:

```powershell
winget install --id Git.Git -e --source winget --accept-package-agreements --accept-source-agreements
```

Close PowerShell and open it again as Administrator, so it finds `git`. Then:

```powershell
git clone <repository URL> C:\reelguo
cd C:\reelguo
git checkout main
```

### Step 3. Run the setup

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\staging\setup.ps1 -AppUrl https://staging.yourdomain.com -TunnelToken <token from step 1>
```

The script:

1. **Checks the server.** It must run as Administrator; it also checks free disk space.
2. **Writes the settings.** It creates `C:\reelguo-staging\staging.env` with new secrets: the media and sign-in keys,
   the admin password, and the database passwords. Access to the folder is limited to SYSTEM and Administrators. If
   the file already exists, its values and secrets are kept.
3. **Installs the tools:** Git, Node.js (the current LTS, 22.12 or newer), the .NET 10 SDK and cloudflared through
   winget; Caddy and ffmpeg by download. pnpm comes through corepack, at the version the repository asks for. Node.js
   25 and later no longer include corepack, so the script installs it with npm first.
4. **Installs PostgreSQL 17** as the Windows service `postgresql-x64-17`, listening on this server only. It then
   creates the app's database (UTF-8) and login.
5. **Builds the first release** (API, worker, web app, admin console). This takes 5–15 minutes the first time.
6. **Creates the Windows services** `ReelGuoApi`, `ReelGuoWorker`, `ReelGuoWeb` and `cloudflared`. They start
   automatically at boot, with nobody signed in, and restart themselves after a crash.
7. **Starts everything**, waits until the site is ready (the database tables are created on the first start), and
   checks the site.
8. **Schedules the nightly database backup** at 03:30.
9. **Loads the demo content:** 4 series × 5 episodes, encoded by the worker, then published, plus sample posts. Use
   `-SkipDemo` to leave it out.

At the end it prints the **admin password** once. Save it in your password manager; it is also in
`C:\reelguo-staging\staging.env` as `REELGUO_ADMIN_PASSWORD`. The script is safe to run again after fixing a
problem.

### Step 4. Point the staging address at the tunnel

Back in **Zero Trust → Networks → Tunnels → reelguo-staging → Public hostname → Add a public hostname**:

| Field | Value |
|---|---|
| Subdomain / Domain | `staging` / `yourdomain.com` (must match `-AppUrl`) |
| Service type | `HTTP` |
| URL | `localhost:8080` |

Cloudflare creates the DNS record itself.

The admin console is not public. On the server, open **http://localhost:8081**; use `localhost`, not `127.0.0.1`,
because the sign-in cookie needs it. To reach it from elsewhere, add a second public hostname, for example
`staging-admin` → `HTTP` `localhost:8081`. **Protect it first:** **Zero Trust → Access → Applications → Add an
application → Self-hosted**, for that hostname, with a policy that allows only your team's email addresses.

### Step 5. Cloudflare settings for the domain

- **SSL/TLS → Edge Certificates → Always Use HTTPS**: on.
- **Network → IP Geolocation**: on (the default). The site reads the visitor's country from it, for the country block
  list and the age rules.
- **Caching:** no "Cache Everything" rules for the staging host. Pages differ per country and per visitor; static
  files are cached correctly by default.

### Step 6. Check the site

- Open `https://staging.yourdomain.com`. The 18+ page appears; after confirming, the demo series are on the home
  page and play.
- `https://staging.yourdomain.com/robots.txt` must show `Disallow: /`.
- Sign in to the admin console with user `admin` and the password from step 3.
- Run `.\scripts\staging\ops.ps1 status`. Every line should say `ok`.

### Step 7. After the first sign-in

- Create named admin accounts for the team (**管理员**), then change the `admin` password there.
- If you change it, `seed-demo.ps1` needs the new one: `seed-demo.ps1 -AdminPassword <new password>`.
- Keep a copy of `C:\reelguo-staging\staging.env` in your password manager. Without its keys and passwords, a
  rebuilt server can't continue where this one left off.

### Without a tunnel: Cloudflare DNS straight to the server (public port)

If the domain's DNS records already point at the server through Cloudflare, no tunnel is needed. Cloudflare connects
to the server on port 80, and Caddy tells the site and the admin console apart by host name. Use this instead of
steps 1, 3 and 4 above.

1. **Cloudflare DNS:** `A` records to the server's public IP, both **Proxied** (orange cloud): one for the site (for
   example `@` or `staging`) and one for the admin console (for example `admin`).
2. **Cloud security group** (Tencent: 安全组): allow inbound **TCP 80 only from Cloudflare's addresses**
   (https://www.cloudflare.com/ips/; an IP address group / 参数模板 makes them one entry), and RDP 3389 only from your
   own IP. Tencent's Windows images often ship with Windows Firewall turned off, so the security group is what stops
   others from reaching the server directly. They could otherwise pretend to be Cloudflare and fake a visitor's
   country.
3. **Setup:**

   ```powershell
   .\scripts\staging\setup.ps1 -Mode public-port -AppUrl https://yourdomain.com -AdminHost admin.yourdomain.com
   ```

   Caddy listens on port 80 on every network interface. Requests for the admin address (`REELGUO_ADMIN_HOST`) get the
   admin console; every other host name gets the site. On the server the console also stays at http://localhost:8081.
   The script adds a Windows Firewall rule for Cloudflare's addresses, and warns if Windows Firewall is off.
4. **SSL/TLS → Overview → Flexible.** The server speaks plain HTTP; visitors still get HTTPS from Cloudflare. With
   Full or Full (strict), Cloudflare tries HTTPS to the server and fails with error 521 or 525.
5. **Protect the admin address:** **Zero Trust → Access → Applications → Add an application → Self-hosted** →
   `admin.yourdomain.com`, policy *Allow* for your team's email addresses. Do this before anyone else knows the
   address; without it, only the admin password stands in front of the console.
6. Then continue with steps 5 to 7 above. Also check from another machine that `http://<server IP>/` does **not**
   answer: the security group must block it.

## 3. Updating staging (every new version)

1. Push the new version to the branch staging follows.
2. On the server, in PowerShell as Administrator:

   ```powershell
   cd C:\reelguo
   Set-ExecutionPolicy -Scope Process Bypass
   .\scripts\staging\update.ps1
   ```

The script:

1. **Checks** the server and the settings.
2. **Fetches the code** with `git pull --ff-only`. It stops if someone has edited files on the server; see §8.
3. **Waits while an admin is optimizing or uploading videos** in the admin console (优化视频, 文件夹上传), so
   their work is never cut off. The console reports such work every 30 s; the script asks the API directly on the
   server (`/health/busy`, which answers nothing that came through Caddy or Cloudflare), shows who is working and how
   far they are once a minute, and continues by itself when they finish. It checks again right before step 5, in case
   work started while the release was building. Ctrl+C cancels safely (nothing has changed yet); `-Force` skips the wait.
   Then it **backs up the database.** If the backup fails, it stops before changing anything.
4. **Builds the new release** into its own folder while the current version keeps running.
5. **Switches to it:** it stops the services, points `current` at the new release, and starts them. The site is down
   for about a minute. Database migrations run when the API starts.
6. **Waits until the site is ready**, runs the checks, and keeps the last 5 releases.
7. **Records the deploy** in `C:\reelguo-staging\deploy.log`: time, action, release and result.

| Option | Use |
|---|---|
| `-Ref <branch>` | Switch to another branch and follow it, for example `-Ref release/1.2`. |
| `-Ref <tag or commit>` | Deploy one fixed version. Plain updates then stop until you choose a branch again with `-Ref main`. |
| `-SkipPull` | Deploy the code already in `C:\reelguo` (for example copied over by hand). |
| `-SkipBackup` | Skip the database backup (not advised). |
| `-AllowDirty` | Continue although files in `C:\reelguo` were changed on the server. |
| `-Force` | Update at once, even while an admin is optimizing or uploading videos. Their work stops: 文件夹上传 continues by itself afterwards (持续上传), and 优化视频 offers 继续优化 with the same folders. |

Changed only `staging.env`? You don't need an update: run `.\scripts\staging\ops.ps1 config`, which writes the
settings into the running release and restarts it.

### If an update fails

When the new version doesn't become ready, the script prints the recent logs and the ways back. It doesn't roll
back by itself, because the database may already have been migrated:

```powershell
.\scripts\staging\rollback.ps1                                   # the previous release, database as it is
.\scripts\staging\rollback.ps1 -RestoreBackup <backup file>      # the previous release AND the database from before the update
```

## 4. Rolling back

| Command | What it does |
|---|---|
| `rollback.ps1` | Switches back to the release before the current one, within seconds. The database isn't touched. |
| `rollback.ps1 -To <release>` | Switches to a specific release. |
| `rollback.ps1 -List` | Lists the releases (the running one marked) and the backups. |
| `rollback.ps1 -RestoreBackup <file>` | The previous release, **and** the database replaced by that backup in one all-or-nothing step. Everything saved after the backup is lost (new accounts, comments, admin edits); media files are kept. It asks you to type the file name to confirm (`-Yes` skips that). |

Rolling back doesn't change `C:\reelguo`. Before the next update, check out the version you want; the commit is the
last part of each release name.

## 5. Day to day

| Command | What it does |
|---|---|
| `ops.ps1 status` | Services, readiness, the site checks, the running release and the last deploys. |
| `ops.ps1 logs [api\|worker\|web\|postgres\|tunnel]` | Recent log entries. The API and worker log to the Windows Event Log (Application, sources `ReelGuo.Api` and `ReelGuo.Worker`); the web server logs to `logs\caddy.log`. |
| `ops.ps1 restart [service]` | Restarts one service, or everything. |
| `ops.ps1 stop` / `ops.ps1 start` | Stops ReelGuo (the database keeps running) or starts it again. |
| `ops.ps1 config` | Applies changes from `staging.env` to the running release and restarts it. |
| `ops.ps1 backup` / `ops.ps1 backups` | Backs up the database now, or lists the backups. |
| `ops.ps1 disk` | Space used by releases, media, backups, tools and the database. |

**Backups.**
- **Schedule:** the scheduled task "ReelGuo staging backup" runs `backup.ps1` every night at 03:30. It writes a
  `pg_dump` archive with a `.sha256` checksum and keeps them for `REELGUO_BACKUP_KEEP_DAYS` days (default 14).
- **Off the server:** copy `C:\reelguo-staging\backups` off the server regularly, for example to object storage. A
  backup on the same disk doesn't survive losing that disk.

**After a server restart** (for example Windows updates), all services start by themselves; nobody needs to sign
in. Check with `ops.ps1 status`.

**Demo content.**
- `seed-demo.ps1` skips when published series exist; `-Force` adds another set.
- When the reviewed catalogue arrives, take the demo series and posts down in the admin console (**内容管理**,
  **吃瓜文章**). Their titles end with "（示例）".

**Disk space.** Watch the free space on C: (`ops.ps1 disk`). The media folder grows with every upload. Each release
takes about 150 MB, and the last 5 are kept.

## 6. Real videos: Tencent COS

The demo content is transcoded on this server. The real videos are stored the way the Viora (ReelPico) platform
stores them: in a **private Tencent COS bucket**. The admin's browser uploads each file **straight to the bucket**
with a one-time signed link, so no video passes through this 4 GB server or through Cloudflare. Viewers play the
MP4 from the bucket with links that expire after 30 minutes. COS handles range requests, so playback starts and
seeks before the whole file has arrived.

```
admin's PC ──(signed PUT, one file)──▶ COS bucket  videos/<storage folder>/<title folder>/<file name>
     │                                      ▲   │
     └── admin console: plan, confirm ──▶ API   └──(signed GET, 30 min)──▶ viewers' players
                                            │
                     worker: reads the file's header from COS (ffprobe) + a poster frame; nothing is re-encoded
```

> **Before the real catalogue goes up: Tencent's terms.** Tencent Cloud's Acceptable Use Policy prohibits
> sexually explicit content (https://www.tencentcloud.com/document/product/301/9245). The Viora platform's own
> vendor records say its COS account was "cleared" by a partner, but Tencent's **written** confirmation was still
> pending. ReelGuo is an 18+ site: get that confirmation (or choose another store) before uploading real content.
> An account suspension would take the videos offline.

### What the files must be

Nothing re-encodes a COS video, so every file has to play in every browser as it is: **MP4, H.264 video, AAC
audio, with the index at the front** ("faststart"). The folder upload page checks each file's header and holds
back the ones that don't qualify (格式不支持). It also notes files above 8 Mbit/s: they upload, but stall on phones and
cost far more COS traffic.

Deliveries often come with the index at the end and at high bit rates. Convert them before uploading, in one of two
ways.

**In the admin console: 文件夹上传 → 优化视频** (Edge or Chrome on a PC).

1. Pick the delivery folder, then an empty output folder.
2. The page lists every episode: those that need optimising (and why) and those copied as they are.
3. **开始优化** converts them in the browser, one at a time, with the PC's graphics hardware where available:
   H.264 + AAC, index at the front, constant quality. Measured on a real episode: 16 Mbit/s became 1.6 Mbit/s at
   SSIM 0.989, about 80 MB for 6 minutes.
4. The output is written as `Videos/<title>/<title>_<n>.mp4`, `Images/<title>.jpg` and `VideoDetails/`.
5. **上传优化后的文件夹** loads it straight into the upload.

Keep the page open while it works. Started again, it skips finished episodes. Speed depends on the PC: with hardware
encoding usually several times real time; a PC without it encodes in software at about real time.

**On the PC with PowerShell** (faster on a strong CPU, and for very large batches): `scripts\prepare-videos.ps1`. It
writes a copy with the same layout, converts every video, copies the pictures and details files, and skips what it has
already done:

```powershell
cd C:\Users\<you>\Documents\ReelGuo        # the repository on the PC that uploads
powershell -ExecutionPolicy Bypass -File .\scripts\prepare-videos.ps1 -Source "D:\deliveries\SeriesA"
# writes D:\deliveries\SeriesA-upload: pick that folder on the upload page
```

- **Default (compress):** H.264 High at CRF 23, capped at 4 Mbit/s, AAC 128 kbit/s, at most 1080 px on the short
  side. Measured on a real 6-minute 1080×1920 episode: 694 MB at 16 Mbit/s became 88 MB at 2 Mbit/s, looking nearly
  the same (SSIM 0.99), in about a minute on an 8-core PC. Uploads get about 8 times faster.
- **`-Quality high`:** CRF 20, up to 6 Mbit/s; larger files, about twice the time.
- **`-Mode faststart`:** only moves the index, without re-encoding. Takes seconds, but the size stays the same, and the
  codecs must already be H.264 and AAC.

It uses ffmpeg from the repository's `.tools`, from PATH, or downloads it once. Run it again while a delivery is still
downloading: files written in the last minute are left for the next run.

### Step 1. The bucket

Use the **international console** (console.tencentcloud.com) → **Cloud Object Storage (对象存储)**.

- **A bucket of its own, not shared with Viora or any other platform.** ReelGuo deletes a video from the bucket
  when the episode or series using it is deleted in admin, or when the episode's video is replaced, so nothing is left
  behind as an orphan. A file still used by another episode is kept. It never overwrites an existing object: a file
  already in the bucket with the same name and size is **linked, not uploaded again**.
- **A new bucket:** **Create Bucket (创建存储桶)** → region **Singapore (`ap-singapore`)** → access **Private
  Read/Write (私有读写)**, never public. The console appends the APPID, so the real name looks like
  `reelguo-1300000000`; use the full name.

### Step 2. CORS: let the admin console upload

Bucket → **Security Management → CORS (安全管理 → 跨域访问 CORS 设置)** → add a rule. Without it, the upload fails in
the browser with a CORS error and no useful message.

| Field | Value |
|---|---|
| Origin | Every address the admin console is opened from, exactly: its Cloudflare address (for example `https://admin.yourdomain.com`) and `http://localhost:8081` (the console on the server itself). |
| Methods | `PUT`, `GET`, `HEAD` |
| Allow-Headers | `*` |
| Expose-Headers | `ETag`, `Content-Length` |
| Max-Age | `600` |

Viewers don't need a CORS rule: the player loads the MP4 as plain media.

### Step 3. A key that can only reach this bucket

**Cloud Access Management (访问管理 / CAM)** → **Users** → create a sub-account with **programmatic access only**. Give
it a policy limited to this one bucket: read, write, list **and delete** (`cos:DeleteObject`), not
`AdministratorAccess` and not all of COS. Copy its **SecretId** and **SecretKey**. Without delete permission, deleting
content in admin still works, but its videos stay in the bucket: the delete dialog then reports how many could not be
removed, and **运行追踪 → 日志** lists their keys.

### Step 4. Settings

In `C:\reelguo-staging\staging.env` (an update adds these lines if they are missing):

```
REELGUO_VIDEO_PROVIDER=Cos
REELGUO_COS_SECRET_ID=AKID...
REELGUO_COS_SECRET_KEY=...
REELGUO_COS_BUCKET=reelguo-1300000000
REELGUO_COS_REGION=ap-singapore
REELGUO_COS_FOLDER=reelguo
```

Then run `.\scripts\staging\ops.ps1 config`. If a COS setting is missing or the bucket name has no APPID, the script
and the API both stop and say which. Demo episodes encoded before the switch keep playing from the server.

### Step 5. Upload the delivery folder

Admin console → **文件夹上传**:

1. Fill in the settings at the top.
   - **存储文件夹:** pick a folder under `videos/` that is already in the bucket, or type a new name.
   - **新剧放入频道:** the channel new series go to.
   - **版权信息** (optional): copied into each new series that has none. Left empty, a new series gets rights holder
     `huangyueai`, worldwide, and "no" for AI-generated and real person. None of it is required to publish.
2. **选择文件夹:** pick the whole delivery folder. Both layouts work, and a folder holding several titles too:
   - `VideoDetails/`, `Images/<title>.jpg`, `Videos/<title>/<title>_<n>.mp4`
   - `<title>/video/<title>_<n>.mp4` with `<title>/Images/<any name>.jpg`: the title comes from the file names, and
     the tallest picture in a title's `Images` folder is its cover.

   Episode files must be named `<title>_<n>.mp4`. Chrome and Edge remember the folder; other browsers ask each time.
3. The page reads each file's header (a few KB per file) and labels each title: new, has updates, in sync, or needs
   attention. Click a title to see its episodes, coloured by state, and hover an episode to see why.
4. Press **全部上传**:
   - Each title is created as a **draft** series. The title, synopsis, genres and episode total come from its JSON,
     or from the folder name if there is none. Its picture becomes the cover.
   - Its finished episodes are uploaded **two at a time, in order**, each retried three times.
   - Episodes already in the bucket are linked instead of uploaded.
   - Pause and stop work at any moment. A stopped upload is simply sent again next time.
5. **自动上传新文件** (on by default, Chrome and Edge only): leave the tab open. Every 3 minutes the page checks the
   folder again and sends what has finished downloading since. The PC is kept awake while it uploads.
6. When the worker has processed the episodes (seconds each), open the series in **内容管理**, check it and publish.

Each file lands at `videos/<storage folder>/<title folder>/<file name>`, exactly as named on the PC. If another
episode already uses that name, the new file gets `~<series>-<episode>` before `.mp4`. Single episodes uploaded from the
series editor go to `videos/<REELGUO_COS_FOLDER>/<series title>/<file name>`.

**Speed.** The upload runs at the PC's upload speed: at 5 Mbit/s, 600 GB takes about 11 days. For the first bulk
upload, open the console on a rented cloud machine in Singapore instead. The Viora notes suggest Tencent Lighthouse,
about US$12 for a month.

### Step 6. Check

- Open an uploaded episode on the site: it plays and seeks. In the browser's network panel the video comes from
  `<bucket>.cos.ap-singapore.myqcloud.com`.
- A viewer in a blocked country gets no link, and a taken-down series stops issuing links at once. Links already
  handed out stop working within `REELGUO_COS_PLAYBACK_MINUTES` (30).
- Set a **billing alert** in Tencent Cloud: COS bills storage and, above all, outbound traffic.

| If it fails | Look at |
|---|---|
| Upload stops at 0% and the browser console mentions CORS | Step 2: the origin must match exactly, including `https://` and the port. |
| Upload answers 403 | The key (Step 3), the bucket name (it must include the APPID) or the region. |
| "COS 中的文件大小与本地文件不一致" | The upload was cut short. Upload that title again; the episode is sent again. |
| An episode shows 格式不支持 | Not H.264/AAC, or the index isn't at the front. Convert the folder with 优化视频 or `scripts\prepare-videos.ps1` (above), then upload the converted folder. |
| 优化视频 says the browser can't encode H.264 | An old browser, or one without video encoding. Update Edge / Chrome, or use `scripts\prepare-videos.ps1`. |
| A series is named "video", or episodes show 有多个第 1 集的文件 | An admin console from before 2026-11-17, which grouped `video/` folders together. Update staging. |
| An episode is "failed" after upload | `ops.ps1 logs worker`. The worker reads the file from COS, so it needs outbound HTTPS to the bucket. |
| Plays, but only after a long wait | The file isn't faststart. |
| Playback stops after a while with an error | The link expired while the tab was paused; the player fetches a new one. Raise `REELGUO_COS_PLAYBACK_MINUTES` if needed. |

## 8. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| "Run PowerShell as Administrator" | Right-click PowerShell → **Run as administrator**. |
| A winget install fails | Install that tool by hand (Git, Node.js LTS, .NET 10 SDK, cloudflared) and run `setup.ps1` again. It skips what is already installed. |
| "… is not recognized" (`git`, `node`, `pnpm`, `corepack`) right after an install | The new PATH reaches new windows only. Close PowerShell, open it again as Administrator and run the script again. |
| The admin console or the site on this server takes about 2 seconds to answer the first time | An old release whose Caddy listens on `127.0.0.1` only, while `localhost` tries `::1` first. `update.ps1` or `ops.ps1 config` writes the current Caddyfile, which listens on both. |
| "Could not download the PostgreSQL installer" | Download *PostgreSQL 17 Windows x86-64* from EnterpriseDB and install it with the defaults. Put the password you chose in `REELGUO_PG_SUPERPASSWORD`, then run `setup.ps1` again. |
| The build fails (`dotnet publish` or `pnpm`) | Usually network access to nuget.org or the npm registry. Run the same script again. With 4 GB RAM, close other programs during the build. |
| "The site did not become ready" | Read the printed logs, or `ops.ps1 logs api`. Common causes: PostgreSQL isn't running (`ops.ps1 logs postgres`), or the disk is full. |
| Something fails while the site is running (an upload, a page, a worker job) | Admin console → **运行追踪**: the failed request or job is listed with each step's error, and the 日志 tab has the error logs. |
| Cloudflare error **1033** | The tunnel isn't connected. Check `ops.ps1 logs tunnel` and the tunnel's page in Cloudflare; usually a wrong or old token. Put the new token in `CLOUDFLARE_TUNNEL_TOKEN`, then run `ops.ps1 config`. If the tunnel still won't connect, check that the server allows outbound traffic on port 7844. |
| Cloudflare **502 Bad Gateway** | The public hostname's service is wrong. It must be `HTTP` and `localhost:8080` (admin: `localhost:8081`). Also check that the service `ReelGuoWeb` is running. |
| Cloudflare **521** (public-port mode) | The server isn't reachable on port 80. Check the cloud firewall, the Windows Firewall rule "ReelGuo staging (Cloudflare only)", and that `REELGUO_WEB_PORT` is 80. Also check that SSL/TLS is **Flexible**. |
| "Port 80 is already in use by Windows HTTP.sys (usually IIS)" | IIS isn't needed (Caddy is the web server). Stop it: `Stop-Service W3SVC -Force; Set-Service W3SVC -StartupType Disabled`, or remove it with `Uninstall-WindowsFeature Web-Server`, then run `setup.ps1` again. |
| Cloudflare **525** or **526** (public-port mode) | SSL/TLS is set to Full or Full (strict). Set it to **Flexible**: the server speaks plain HTTP. |
| `admin.yourdomain.com` shows the site, not the admin console | `REELGUO_ADMIN_HOST` is empty or different. Set it in `staging.env` to exactly that host name, then run `ops.ps1 config`. |
| Every visitor's country is "XX", or country rules don't apply | IP Geolocation is off in Cloudflare (Network settings). |
| Can't stay signed in to the admin console on the server | Open `http://localhost:8081`, not `127.0.0.1`. The sign-in cookie needs a secure address, and browsers count `localhost` as one. |
| `seed-demo.ps1` fails | Check `ops.ps1 logs worker` (it encodes the clips). If the admin password was changed, pass it with `-AdminPassword`. |
| update: "There are uncommitted changes" | Files in `C:\reelguo` were edited. Look with `git status`. Discard with `git checkout -- .`, or commit them to the repository instead. |
| update: "This folder is on a fixed version" | It was last deployed with `-Ref <tag>`. Run `update.ps1 -Ref main` to follow a branch again. |
| The disk is full | `ops.ps1 disk`. Old releases beyond the last 5 are removed automatically. Check the media folder and backups. |

## 9. Security notes

- **`C:\reelguo-staging\staging.env` holds the secrets.** The folder is readable only by SYSTEM and Administrators.
  Keep a copy in a password manager, and never paste it into tickets or chats.
- **The services run as LocalSystem.** That keeps setup simple on a dedicated staging server. Don't run other
  people's software on it.
- **PostgreSQL listens on this server only.** The app's database login can only reach its own database.
- **The admin console is local-only** (port 8081 on `127.0.0.1` and `::1`) unless you publish it. Publish it through
  the tunnel, or as `REELGUO_ADMIN_HOST` in public-port mode, and always behind a Cloudflare Access policy.
- **Public-port mode:** port 80 must be open to Cloudflare only (security group). Otherwise anyone can reach the server
  directly and send fake Cloudflare headers, for example a false visitor country.
- **Staging stays out of search engines.** Check after changes that `/robots.txt` says `Disallow: /`.
- **The COS key can write to the bucket.** It is only in `staging.env` and the generated release settings. Keep it
  limited to the one bucket (§6, step 3), and rotate it in CAM if it leaks.
- **Sandbox payments are off.** If you turn them on for testing, anyone can top up for free, so never on production.
- **Production differs from staging.** Production follows `docs/RUNBOOK.md` §10 (Before launch).
